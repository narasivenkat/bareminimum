Orchestrator & Sub-Agent Architecture

A guide to concurrent read task parallelization and serialized write execution in Agentic Systems.

1. Overview

When building scalable agentic coding tools, workload distribution across multiple LLM instances (sub-agents) significantly reduces latency and increases task completion speed. However, applying concurrency blindly across all operations introduces severe concurrency bugs, data corruption, and race conditions.

To achieve high performance while maintaining system consistency, we use an Orchestrator-Sub-Agent pattern with strict operational boundaries:

Operation Type Tools Included Execution Mode Concurrency Rationale
Read Operations list_dir, read_file, file_search Parallel (Sub-Agents) Stateless, non-mutating, idempotent operations safely scale across concurrent threads/workers.
Write Operations write_file (and directory mutations) Sequential (Orchestrator Queue) Mutating state requires strict synchronization to avoid race conditions, overwrites, and partial state corruption.

2. Architecture Pattern

The Orchestrator Agent operates as the central control node. It parses high-level user goals, divides read-heavy exploration tasks among specialized Sub-Agents (Workers), collects sub-agent insights, and executes write mutations sequentially.

3. Parallelizing Read Tasks

Read operations are state-agnostic and read-only. Consequently, spawning sub-agents to inspect multiple directories or files simultaneously yields massive performance improvements.

Key Read Tools Safe for Concurrency:

  • list_dir: Allows sub-agents to scan multiple subdirectories in parallel to build repository structures.
  • file_search: Enables concurrent pattern matching across distinct sub-trees.
  • read_file: Enables multiple sub-agents to inspect individual source files concurrently without blocking each other.
Performance Gain: In a multi-file codebase search, running 5 sub-agents concurrently to inspect relevant modules reduces exploration wall-clock time by 70–80% compared to sequential tool calls.

3.1 Who Decides to Parallelize: the LLM or the Orchestrator Code?

A common point of confusion is where the parallelization decision actually lives. The answer is that responsibility is split across two layers: the LLM reasons about what can run in parallel, while the orchestrator code enforces how it runs safely. Neither layer owns the decision alone.

Decision Owner What It Determines
Which reads are independent LLM The model understands task intent and emits multiple independent read tool calls in a single turn (e.g., “read config.py AND main.py AND search for db_connect”).
Whether to execute them concurrently Orchestrator Code The harness detects that the batched calls are all read-only and dispatches them together via asyncio.gather — deterministically, without asking the model.
Concurrency limits & safety Orchestrator Code The code caps fan-out with a Semaphore, isolates per-task errors, and forces writes through a serial queue regardless of what the LLM requests.

Two Models of Control

There are two practical ways to wire this up, and most production harnesses use the hybrid of both:

  • LLM-driven (dynamic) parallelism: The model explicitly decides the degree of parallelism by choosing how many independent read tool calls to emit per turn. This is flexible and adapts to the task, but it is non-deterministic and spends reasoning tokens to make the call.
  • Code-driven (deterministic) parallelism: The orchestrator code inspects the batch of tool calls the model returned, classifies each as read vs. write, and automatically runs all reads concurrently while serializing writes. The model does not need to “know” about threads or locks — it just requests data, and the harness decides the safe execution strategy.
Recommended pattern (hybrid): Let the LLM decide what to read in parallel by surfacing independent read requests in one turn, and let the orchestrator code decide how to run them — fanning out read-only calls with asyncio.gather while unconditionally routing every write_file through the serialized mutex queue. This keeps the intelligence in the model and the safety guarantees in deterministic code.
Anti-pattern: Do not let the LLM decide whether writes may run in parallel. Write serialization must always be enforced by the orchestrator code, because the model has no reliable visibility into file locks, dependency ordering, or peer sub-agent mutations.

4. Serializing Write Tasks (Why Writes Must NOT Be Parallelized)

While parallel reads accelerate codebase analysis, write tasks must remain strictly sequential. Writing files asynchronously across multiple sub-agents introduces severe flaws:

Critical Hazards of Parallel Writes:
  • Race Conditions & Lost Updates: If two sub-agents write to the same file or overlapping files simultaneously, one worker's output will overwrite the other's without notice.
  • Inconsistent Code State: File updates often depend on specific ordered prerequisites (e.g. creating a utility function before referencing it in another file). Out-of-order execution breaks build syntax.
  • Token & Context Drift: Sub-agents modifying files in parallel lack visibility into modifications made by peer sub-agents, leading to conflicting code changes.
  • File System Locks: Concurrent disk writes can produce IO errors or locked handle exceptions on Windows and POSIX filesystems.

4.1 Human-in-the-Loop (HITL) Gate Integration in Serialized Writes

In addition to preventing race conditions and file corruption, serializing write tasks via an asyncio.Lock() write mutex (_write_lock) is essential for clean Human-in-the-Loop (HITL) approval interaction.

When a write tool operation (write_file / create_file) is executed by the Orchestrator or a sub-agent:

  • Unified Diff Previews: A line-by-line diff preview (difflib.unified_diff) comparing existing disk content to proposed edits is rendered to stdout for user inspection.
  • Interactive Approval Gate: Execution pauses at Approve file write to '<path>'? [y/N]: awaiting explicit user confirmation (`y`/`yes`).
  • Prompt Serialization: The write mutex ensures that only one sub-agent requests HITL approval at a time. Without serialization, concurrent sub-agents would attempt to read STDIN and output diff previews simultaneously, causing scrambled terminal output and input race conditions.

5. Orchestrated Execution Workflow

  1. Phase 1: Task Decomposition (Orchestrator)
    The main agent receives a complex prompt (e.g. "Refactor error handling across all API routes") and breaks it into independent exploration targets.
  2. Phase 2: Parallel Read Dispatch (Sub-Agents)
    The Orchestrator invokes sub-agents in parallel using async task gatherers. Sub-Agent A calls file_search, Sub-Agent B calls list_dir, and Sub-Agent C calls read_file.
  3. Phase 3: Insights Aggregation (Orchestrator)
    Sub-agents report findings back to the Orchestrator. The Orchestrator constructs a coherent, centralized patch plan.
  4. Phase 4: Serialized Write Queue (Orchestrator)
    The Orchestrator processes file modifications sequentially using write_file, verifying dependencies step-by-step.

6. Code Implementation Example

Below is a production-ready Python pattern demonstrating asynchronous parallel sub-agent reads coupled with a synchronized write queue.

import asyncio
import logging
from typing import List, Dict, Any

# Mock Agent Tool Definitions
async def async_read_file(path: str) -> str:
    """Read file concurrently (Safe for Parallelization)."""
    logging.info(f"[READ START] Reading file: {path}")
    await asyncio.sleep(0.5)  # Simulate I/O latency
    return f"Contents of {path}"

async def async_list_dir(path: str) -> List[str]:
    """List directory contents concurrently."""
    logging.info(f"[READ START] Listing dir: {path}")
    await asyncio.sleep(0.3)
    return ["file1.py", "file2.py", "utils.py"]

async def async_file_search(pattern: str) -> List[str]:
    """Search workspace files concurrently."""
    logging.info(f"[READ START] Searching pattern: {pattern}")
    await asyncio.sleep(0.4)
    return ["auth/login.py", "auth/token.py"]

# Write Queue Lock for Strict Serialization
write_lock = asyncio.Lock()

async def synchronized_write_file(path: str, content: str) -> bool:
    """Write file strictly sequentially using asyncio Lock."""
    async with write_lock:
        logging.info(f"[WRITE START] Writing to {path} (Lock Acquired)")
        await asyncio.sleep(0.6)  # Simulate write latency
        logging.info(f"[WRITE SUCCESS] Finished writing {path}")
        return True

# Sub-Agent Handler for Read Operations
async def sub_agent_read_task(task_type: str, target: str) -> Dict[str, Any]:
    """Sub-agent worker executing read operations concurrently."""
    if task_type == "read_file":
        res = await async_read_file(target)
    elif task_type == "list_dir":
        res = await async_list_dir(target)
    elif task_type == "file_search":
        res = await async_file_search(target)
    else:
        raise ValueError(f"Unknown read task type: {task_type}")
    
    return {"task_type": task_type, "target": target, "result": res}

# Orchestrator Workflow
async def run_orchestrator():
    logging.basicConfig(level=logging.INFO, format="%(asctime)s [%(levelname)s] %(message)s")
    print("=== Phase 1: Dispatching Sub-Agents for Parallel Reads ===")
    
    # Define parallel read targets
    read_tasks = [
        sub_agent_read_task("list_dir", "src/"),
        sub_agent_read_task("file_search", "*.py"),
        sub_agent_read_task("read_file", "src/config.py"),
        sub_agent_read_task("read_file", "src/main.py"),
    ]
    
    # Execute all read tasks concurrently via asyncio.gather
    read_results = await asyncio.gather(*read_tasks)
    print(f"\nCollected {len(read_results)} read results successfully.\n")

    print("=== Phase 2: Processing Writes Sequentially ===")
    
    # Planned writes derived from analysis
    planned_writes = [
        ("src/config.py", "# Updated Config\nDEBUG = True\n"),
        ("src/main.py", "# Updated Main\nimport config\n"),
    ]

    # Writes must NOT be run in asyncio.gather! Run sequentially instead:
    for path, content in planned_writes:
        await synchronized_write_file(path, content)

if __name__ == "__main__":
    asyncio.run(run_orchestrator())

7. Implementation using AutoGen

Microsoft AutoGen is a multi-agent framework that simplifies orchestrating multi-agent conversations and tool execution. You can implement the Orchestrator & Sub-Agent pattern in AutoGen by configuring AssistantAgents for parallel exploration and restricting write capabilities to a synchronized execution queue.

AutoGen Component Mapping

Architecture Role AutoGen Primitive Configuration & Tool Assignment
Orchestrator Agent UserProxyAgent or GroupChatManager Coordinates overall workflow, delegates tasks, synthesizes sub-agent insights, and triggers write steps.
Read Sub-Agents Specialized AssistantAgent instances Registered with read-only tools (read_file, list_dir, file_search). Invoked asynchronously via a_initiate_chat.
Sequential Write Executor UserProxyAgent / Dedicated Writer Agent Registered with write_file tool guarded by an asyncio.Lock to enforce strict serial execution.

Parallel Reads & Serialized Writes in AutoGen

In AutoGen, parallel sub-agent execution is achieved using the asynchronous API (a_initiate_chat) combined with asyncio.gather(). This allows multiple explorer sub-agents to scan directories and read target source files concurrently without blocking one another.

To prevent concurrent write conflicts, the write_file tool registered with AutoGen is wrapped with an asyncio.Lock(). Even if multiple tasks attempt to invoke file writes, the mutex lock guarantees that file modifications execute one at a time in sequence.

AutoGen Code Implementation Example

Below is a production-ready Python snippet showing how to build an Orchestrator and Sub-Agent system using AutoGen:

import asyncio
import autogen
from typing import Annotated

# Configure LLM settings for AutoGen agents
llm_config = {
    "config_list": [{"model": "gpt-4o", "api_key": "YOUR_API_KEY"}],
    "temperature": 0.2,
}

# ==========================================
# 1. Asynchronous Read Tools (Parallel-Safe)
# ==========================================
async def async_read_file(filepath: Annotated[str, "Path of file to read"]) -> str:
    """Read file content asynchronously (safe for parallel execution)."""
    print(f"[Sub-Agent Read] Reading: {filepath}")
    await asyncio.sleep(0.3)  # Simulate I/O latency
    return f"Contents of {filepath}"

async def async_list_dir(path: Annotated[str, "Directory path"]) -> str:
    """List directory contents asynchronously."""
    print(f"[Sub-Agent Read] Listing directory: {path}")
    await asyncio.sleep(0.2)
    return "main.py, config.py, utils.py"

async def async_file_search(pattern: Annotated[str, "Search pattern"]) -> str:
    """Search files asynchronously."""
    print(f"[Sub-Agent Read] Searching pattern: {pattern}")
    await asyncio.sleep(0.3)
    return "main.py: line 12, utils.py: line 45"

# ==========================================
# 2. Synchronized Write Tool (Mutex Locked)
# ==========================================
write_lock = asyncio.Lock()

async def async_write_file(
    filepath: Annotated[str, "Path of file to write"],
    content: Annotated[str, "Content to write into file"]
) -> str:
    """Write content to file sequentially using asyncio Lock."""
    async with write_lock:
        print(f"[Orchestrator Write] Lock acquired. Writing to {filepath}...")
        await asyncio.sleep(0.5)  # Simulate disk write latency
        print(f"[Orchestrator Write] Successfully completed write: {filepath}")
        return f"Successfully wrote to {filepath}"

# ==========================================
# 3. AutoGen Agent Definitions
# ==========================================
# Orchestrator agent coordinates tasks and executes tools
orchestrator = autogen.UserProxyAgent(
    name="Orchestrator",
    human_input_mode="NEVER",
    max_consecutive_auto_reply=5,
    is_termination_msg=lambda x: "TERMINATE" in x.get("content", ""),
    code_execution_config=False,
)

# Explorer sub-agent specialized for read operations
explorer_agent = autogen.AssistantAgent(
    name="ExplorerSubAgent",
    system_message="You are a code exploration sub-agent. Inspect and analyze files using read tools.",
    llm_config=llm_config,
)

# Writer agent specialized for code updates
writer_agent = autogen.AssistantAgent(
    name="WriterAgent",
    system_message="You are a code modification sub-agent. Update target files safely.",
    llm_config=llm_config,
)

# ==========================================
# 4. Tool Registration in AutoGen
# ==========================================
# Register read tools to Explorer Sub-Agent
autogen.agentchat.register_function(
    async_read_file,
    caller=explorer_agent,
    executor=orchestrator,
    description="Read contents of a specific file"
)
autogen.agentchat.register_function(
    async_list_dir,
    caller=explorer_agent,
    executor=orchestrator,
    description="List files in a directory"
)
autogen.agentchat.register_function(
    async_file_search,
    caller=explorer_agent,
    executor=orchestrator,
    description="Search codebase for pattern"
)

# Register write tool to Writer Agent
autogen.agentchat.register_function(
    async_write_file,
    caller=writer_agent,
    executor=orchestrator,
    description="Safely write or modify a file"
)

# ==========================================
# 5. Orchestrated Execution Workflow
# ==========================================
async def main():
    print("=== Phase 1: Parallel Read Operations with AutoGen Sub-Agents ===")
    
    # Launch parallel read tasks using AutoGen's async initiation (a_initiate_chat)
    read_task_1 = orchestrator.a_initiate_chat(
        explorer_agent,
        message="Please list contents of directory '.' and read 'config.py'.",
        clear_history=True
    )
    read_task_2 = orchestrator.a_initiate_chat(
        explorer_agent,
        message="Please search for 'db_connect' pattern in codebase.",
        clear_history=True
    )

    # Gather results concurrently
    await asyncio.gather(read_task_1, read_task_2)
    print("\nParallel exploration complete.\n")

    print("=== Phase 2: Serialized Write Operations ===")
    
    # Execute write task sequentially
    await orchestrator.a_initiate_chat(
        writer_agent,
        message="Update 'config.py' with new configuration settings.",
        clear_history=True
    )

if __name__ == "__main__":
    asyncio.run(main())
Key Takeaway for AutoGen: Using a_initiate_chat combined with asyncio.gather allows multiple AutoGen sub-agents to execute read-heavy exploration tasks concurrently, while protecting write tools with an asyncio.Lock ensures that file mutations remain strictly sequential and safe.

8. Best Practices & Guidelines

  • Limit Read Concurrency: Bound the maximum number of concurrent sub-agents using an asyncio.Semaphore(10) to prevent hitting LLM rate limits or exhausting system file descriptors.
  • Single Responsibility Writes: Always delegate write_file tool calls directly to the Orchestrator or run them through a synchronized queue worker.
  • Pre-Condition Validation: Before executing a sequential write, verify that the target file hasn't changed since the initial read step (e.g., hash or timestamp checks).
  • Error Isolation: If a parallel sub-agent fails during a read task, log the failure and allow remaining sub-agents to complete without aborting the whole run.
