File-Based Graph Storage vs. Neo4j

Options, trade-offs, and recommendations for storing the BareMinimum code-knowledge graph as one or more files instead of a Neo4j database.

Graph Storage JSON / JSONL Kùzu Embedded SQLite NetworkX

Executive Summary

Today, bareminimum builds its code-knowledge graph inside a Neo4j database. The ingestion pipeline (graph/ingester.py) parses source files into ASTs, call graphs, endpoint mappings, and documentation links, then the inserter (graph/neo4j_inserter.py) writes them as nodes (File, Class, Method, Endpoint, Document, ASTNode) and relationships (DEFINES, HAS_METHOD, CALLS, HANDLED_BY, DOCUMENTS, CONTAINS_AST). Retrieval (graph/retrieve.py) runs Cypher queries against that database.

Core Question

Is it possible to store the graph as a file (or a few files) instead of in Neo4j? What are the pros and cons?

Short answer: Yes — it is entirely possible, and for a "bare minimum" harness it can be attractive. But the right choice depends on graph size, query complexity, and whether you need multi-hop traversals like the current CALLS*1..2 queries.

1. What the Graph Must Support

Before comparing storage formats, it helps to pin down what the current Neo4j usage actually requires. From graph/retrieve.py, the graph must support:

Node lookup by propertyMATCH (c:Class) WHERE c.name CONTAINS $termEasy

1-hop relationship traversal(f:File)-[:DEFINES]->(c:Class)Easy

⚠ Decisive Factor

The hardest capability to reproduce with plain files is variable-length traversal (CALLS*1..2 and deeper). Keep that in mind when reading the options below.

2. File-Based Storage Options

Option A: Plain JSON / JSONL Graph File(s)

Store the whole graph as one (or a few) JSON documents: an array of nodes and an array of edges, mirroring the in-memory structures the pipeline already builds.

{
  "nodes": [
    { "id": "File:graph/retrieve.py", "label": "File", "path": "graph/retrieve.py", "hash": "a1b2c3" },
    { "id": "Class:GraphRetriever",   "label": "Class", "name": "GraphRetriever" },
    { "id": "Method:execute_cypher",  "label": "Method", "name": "execute_cypher" }
  ],
  "edges": [
    { "from": "File:graph/retrieve.py", "type": "DEFINES",    "to": "Class:GraphRetriever" },
    { "from": "Class:GraphRetriever",   "type": "HAS_METHOD", "to": "Method:execute_cypher" }
  ]
}

Typical layout: one file per repo (<repo>.graph.json), or split by concern (nodes.jsonl, edges.jsonl, docs.jsonl).

Pros

  • Zero infrastructure: No database server, no NEO4J_USERID/NEO4J_PASSWORD, no bolt://localhost:7687 connection. Removes a whole class of setup/auth failures.
  • Human-readable & diffable: Fits the "bare minimum" ethos; the graph can live in Git next to the code and be code-reviewed.
  • Trivially portable: Copy a file to share or cache a graph.
  • Simple incremental writes: The existing hash-tracking logic (get_stored_file_hashes) maps cleanly onto a JSON hash field.

Cons

  • No query engine: You must load the file into memory and implement traversal yourself. Multi-hop queries like CALLS*1..2 become hand-written graph walks (BFS/DFS).
  • Whole-file load: JSON is read all-or-nothing; a large repo graph must be fully loaded into RAM to answer even one query.
  • No concurrency / locking: Two writers can corrupt the file; Neo4j handles transactions.
  • No indexes: Property lookups become O(n) scans unless you build in-memory indexes.
✓ Best when

Small-to-medium repos, single process, graph comfortably fits in memory.

Option B: Embedded Graph Database File (Kùzu)

Use an embedded graph database that stores everything in a local file/directory but still speaks a query language. Kùzu is the closest drop-in: it is embeddable (like SQLite), file-based, and supports Cypher — including variable-length traversals.

Pros

  • Keeps Cypher: Queries like (m)-[:CALLS*1..2]->(callee) work with minimal rewrites, so graph/retrieve.py changes stay small.
  • No server process: The database is a local folder; no daemon, ports, or credentials.
  • Real indexes & out-of-core execution: Scales far past what hand-rolled JSON can do without loading everything into RAM.
  • Transactional: Safe concurrent reads, atomic writes.

Cons

  • New dependency: Adds a library (and a compiled engine) to requirements.txt.
  • Not purely "a file you can read": It's a binary store/directory, not human-diffable.
  • Cypher dialect differences: Not 100% identical to Neo4j; some queries need tweaks.
  • Less ubiquitous: Smaller ecosystem/community than Neo4j.
✓ Best when

You want to drop the Neo4j server but keep rich graph queries and scale.

Option C: SQLite (Relational Tables Emulating a Graph)

Store nodes and edges in a single-file SQLite database: a nodes table and an edges table, with indexes on labels, names, and endpoints.

CREATE TABLE nodes (id TEXT PRIMARY KEY, label TEXT, name TEXT, path TEXT, hash TEXT);
CREATE TABLE edges (src TEXT, type TEXT, dst TEXT);
CREATE INDEX idx_nodes_label ON nodes(label);
CREATE INDEX idx_edges_src   ON edges(src, type);

Pros

  • Battery-included: Python ships sqlite3 in the stdlib — no new dependency.
  • One file, indexed, transactional, concurrent-read-safe.
  • Fast property lookups via SQL indexes; CONTAINS becomes LIKE '%term%'.
  • Mature and ubiquitous.

Cons

  • No native traversal: Multi-hop CALLS*1..2 must be expressed as recursive CTEs (WITH RECURSIVE ...) or multiple self-joins — more verbose and easy to get wrong.
  • Impedance mismatch: Graph semantics bolted onto tables; collecting neighbor sets takes extra joins/grouping.
✓ Best when

You want zero new dependencies, mostly shallow (1–2 hop) queries, and SQL is acceptable.

Option D: NetworkX (In-Memory Graph + File Serialization)

NetworkX is a pure-Python graph library. You build the graph in memory as a DiGraph (or MultiDiGraph), then serialize it to a single file. Because the harness graph is directed (File → Class → Method) and a pair of nodes can be connected by more than one relationship type, a MultiDiGraph is the most faithful fit — it allows parallel edges distinguished by a key (the relationship type).

Dependency

NetworkX is a single pure-Python package with no compiled extensions, so installation is lightweight and cross-platform:

# add to requirements.txt
networkx>=3.0

# or install directly
pip install networkx
  • Pure Python, no native build: unlike Kùzu, there is no C/C++ engine to compile — it installs cleanly in the harness .venv.
  • Optional extras only: core graph storage/traversal needs nothing else. matplotlib/pydot are only needed for drawing, which this use case does not require.
  • Stable, mature API: widely used, so the store/retrieve code below is unlikely to churn.

How Nodes & Edges Are Stored

Each graph element maps directly onto the harness schema. A node's ID is a stable string (e.g. "Method:execute_cypher"), and its properties (label, name, path, hash, …) are stored as an attribute dictionary on the node. Relationships become edges keyed by their type (DEFINES, HAS_METHOD, CALLS, HANDLED_BY, DOCUMENTS, CONTAINS_AST).

import networkx as nx

# MultiDiGraph: directed + parallel edges distinguished by `key` (relationship type)
G = nx.MultiDiGraph()

# --- Nodes: id + property dict (mirrors Neo4j node labels/properties) ---
G.add_node("File:graph/retrieve.py", label="File",
           path="graph/retrieve.py", hash="a1b2c3")
G.add_node("Class:GraphRetriever",   label="Class", name="GraphRetriever")
G.add_node("Method:execute_cypher",  label="Method", name="execute_cypher",
           full_name="GraphRetriever.execute_cypher")

# --- Edges: relationship type carried as the edge `key` + optional props ---
G.add_edge("File:graph/retrieve.py", "Class:GraphRetriever", key="DEFINES")
G.add_edge("Class:GraphRetriever",   "Method:execute_cypher", key="HAS_METHOD")
G.add_edge("Method:execute_cypher",  "Method:_format_records", key="CALLS", line=68)

# --- Serialize the whole graph to one file ---
# Preferred portable/interoperable formats:
nx.write_graphml(G, "myrepo.graphml")        # XML, tool-interoperable
# nx.write_gexf(G, "myrepo.gexf")            # XML, Gephi-compatible

# Node-link JSON (human-readable, diffable, no pickle risk):
import json
json.dump(nx.node_link_data(G), open("myrepo.graph.json", "w"), indent=2)
⚠ Incremental updates & hash tracking

The existing contract get_stored_file_hashes() maps to iterating nodes and reading the hash attribute: {d["path"]: d["hash"] for _, d in G.nodes(data=True) if d.get("label") in ("File", "Document") and d.get("hash")}. On re-ingest, compare hashes, then G.remove_node(...) / G.add_node(...) the changed files before re-serializing.

How Nodes Are Retrieved

Every Cypher method in graph/retrieve.py has a direct NetworkX equivalent. Property lookups become node iteration; 1-hop traversals become successor/predecessor lookups; and the CALLS*1..2 variable-length traversal becomes a bounded BFS — the exact capability a plain JSON file lacks.

import networkx as nx

G = nx.read_graphml("myrepo.graphml")   # load once, query many times

# 1) Property lookup  —  MATCH (c:Class) WHERE c.name CONTAINS $term
def find_classes(term):
    return [n for n, d in G.nodes(data=True)
            if d.get("label") == "Class" and term in (d.get("name") or "")]

# 2) 1-hop forward  —  (f:File)-[:DEFINES]->(c:Class)
def classes_in_file(file_id):
    return [v for _, v, k in G.out_edges(file_id, keys=True) if k == "DEFINES"]

# 3) Reverse 1-hop  —  (caller:Method)-[:CALLS]->(m)   (who calls me?)
def callers_of(method_id):
    return [u for u, _, k in G.in_edges(method_id, keys=True) if k == "CALLS"]

# 4) Variable-length  —  (m)-[:CALLS*1..2]->(callee:Method)
def callees_within(method_id, max_hops=2):
    # bounded BFS following only CALLS edges
    seen, frontier = set(), {method_id}
    for _ in range(max_hops):
        nxt = set()
        for node in frontier:
            for _, v, k in G.out_edges(node, keys=True):
                if k == "CALLS" and v not in seen:
                    seen.add(v); nxt.add(v)
        frontier = nxt
    return seen

# Compose into get_method_context()-style result
def get_method_context(method_id):
    return {
        "method":   G.nodes[method_id],
        "callers":  callers_of(method_id),
        "callees":  list(callees_within(method_id, 2)),   # == CALLS*1..2
        "docs":     [u for u, _, k in G.in_edges(method_id, keys=True)
                     if k == "DOCUMENTS"],
    }

NetworkX also ships higher-level helpers that collapse these walks into one call — e.g. nx.descendants_at_distance(G, m, 2) for reachable callees, nx.single_source_shortest_path_length(G, m, cutoff=2) for hop counts, and nx.ego_graph(G, m, radius=2) to extract a node's local neighborhood as a subgraph.

Pros

  • Rich traversal API: BFS, DFS, shortest paths, ancestors/descendants, ego graphs come for free — directly covers the CALLS*1..2 style needs in Python with far less hand-written code than raw JSON.
  • Pure-Python, lightweight dependency: no compiled engine, installs cleanly into the harness .venv.
  • Flexible serialization: GraphML/GEXF are tool-interoperable; node-link JSON stays human-readable and diffable.
  • Natural property model: node/edge attribute dicts map 1:1 onto Neo4j labels and properties.

Cons

  • Full load into memory to query (same RAM ceiling as JSON); no out-of-core execution.
  • No query language: traversals are imperative Python, so every retrieve.py Cypher method must be re-expressed as code.
  • No built-in indexes: property lookups are O(n) scans unless you maintain side dicts (e.g. name → node_id).
  • No transactions/concurrency: a single process owns the in-memory graph; concurrent writers need external locking.
🔒 Security Note

NetworkX can also pickle graphs (nx.write_gpickle in older versions / pickle.dump), but pickle is unsafe to load from untrusted sources (arbitrary code execution). Never load a pickle file you did not produce yourself; prefer GraphML/GEXF/node-link JSON for shared or checked-in artifacts.

✓ Best when

You want programmatic graph algorithms in-process (multi-hop call chains, reachability, neighborhoods) and the graph comfortably fits in RAM.

4. Impact on This Codebase

Switching from Neo4j to files touches three modules:

graph/dbconn.py

The Neo4jConnection, credential handling, and per-repo database creation would be replaced by a file path (e.g. ./<repo>.graph.json or ./<repo>.kuzu/). Much of the env-var/auth plumbing disappears.

graph/neo4j_inserter.py

Neo4jInserter becomes a file writer. The hash-tracking contract (get_stored_file_hashes) is preserved as a hash field on each File/Document node, so incremental ingestion still works.

graph/retrieve.py

The biggest rewrite. Each Cypher method (get_method_context, get_file_context, …) must be reimplemented per backend — least work with Kùzu, most with JSON/SQLite.

Retriever rewrite effort by backend
  • Kùzu (B): near-identical Cypher — least work.
  • JSON (A) or NetworkX (D): hand-written graph walks for CALLS*1..2.
  • SQLite (C): SQL joins + recursive CTEs for deep traversals.

The ingestion architecture itself (bulk vs. incremental, described in the Ingestion Pipeline Architecture Guide) is orthogonal — it works the same regardless of the storage backend.

✓ Pragmatic Path for BareMinimum

If the goal is to eliminate the Neo4j server dependency while preserving the existing query shape, Kùzu (Option B) is the lowest-friction swap because it keeps Cypher and multi-hop traversals. If the goal is maximum simplicity and the graphs are small, JSON (Option A) best matches the "bare minimum" philosophy — at the cost of writing your own traversal logic for the CALLS*1..2 queries.

6. Key Takeaways

  • Yes, the graph can be stored as a file (or a few files). Several formats work: JSON, embedded graph DB, SQLite, or a serialized graph-library format.
  • The decisive factor is whether you need native multi-hop traversal; the current code relies on CALLS*1..2, which is cheap in Neo4j/Kùzu but manual in JSON/SQLite.
  • File storage removes server/auth/ops overhead and improves portability, but gives up Neo4j's query engine, indexing, out-of-core scaling, and transactions.
  • The ingestion pipeline and incremental hash tracking are backend-agnostic, so only the connection, insert, and retrieve layers need to change.
