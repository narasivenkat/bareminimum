0 Executive Overview: Why Graph RAG for Code Intelligence?

When building AI software engineering agents (such as automated coders, code review tools, or API refactoring assistants), standard context retrieval strategies face a fundamental trade-off between context fragmentation and context bloat.

Standard vector search slices files into arbitrary 500-token chunks, losing critical symbol scope, class hierarchies, and invocation graphs. Conversely, sending whole files easily consumes 30,000–80,000 tokens per prompt turn. Graph RAG bridges this gap by representing ASTs, call graphs, endpoint routing, and documentation links as an interconnected graph, allowing the agent to retrieve only the precise topological sub-graph signatures required (averaging 500–1,500 tokens)—yielding an 85% to 95% reduction in total token usage.

1. Abstract Syntax Trees (ASTs)

What it is: A structural, tree representation of source code syntax generated by parsers (e.g., Tree-sitter, Babel, AST modules). It breaks raw source code into structured lexical nodes such as modules, classes, methods, parameters, and variable definitions.

Graph RAG Role: Captures lexical scoping and symbol definitions (e.g., CLASS_CONTAINS_METHOD) so agents retrieve precise function signatures without sending full body implementations.

2. Call Graphs

What it is: A directed network mapping execution flow and function invocation paths across the codebase (which functions call which other functions).

Graph RAG Role: Enables multi-hop dependency tracing (e.g., CALLS / CALLED_BY) so agents know upstream callers and downstream side-effects across files instantly.

3. Endpoint Routing

What it is: The mapping between external network interfaces (HTTP routes, REST endpoints, GraphQL schemas) and internal controller/service handlers.

Graph RAG Role: Connects incoming API requests (e.g., POST /api/v1/orders) directly to backend execution paths (ROUTES_TO), allowing end-to-end API tracing.

4. Documentation Links & Interconnected Graph

What it is: Explicit relationships linking specs, READMEs, ADRs, and docstrings directly to the corresponding code symbols and routes.

Graph RAG Role: Bridges human natural-language intent with code implementation (DOCUMENTS), allowing seamless traversal between specs and implementation.

1 Should You Use Neo4j for the Graph Database?

Yes, Neo4j is the industry-standard recommendation for Code & Document Graph RAG, though lightweight alternatives exist depending on deployment requirements. Software codebases require deep multi-hop relationship traversals (e.g., finding all callers of a method 4 hops away across repos), vector search for natural language query matching, and flexible schema properties.

Why Neo4j Fits Code & Document Graph RAG

  • Cypher Query Language: Optimized for multi-hop graph traversals (e.g., MATCH (e:Endpoint)-[:ROUTES_TO]->(f:Function)-[:CALLS*1..4]->(d:DatabaseQuery)).
  • Hybrid Vector + Graph Retrieval: Neo4j supports native vector indexing alongside graph edges. Search docstring embeddings to find starting nodes, then traverse AST edges.
  • Scalability: Handles millions of nodes/edges effortlessly for large enterprise mono-repos.
  • Ecosystem: Native integrations with LangChain, LlamaIndex, and Python/JS SDKs.

Alternative Databases to Consider

  • Memgraph: High-performance in-memory property graph DB, fully Cypher compatible. Excellent for low-latency CI/CD agent workflows.
  • KùzuDB: Embedded property graph database (like SQLite for graphs). Ideal if you want zero infra overhead within an agent CLI tool.
  • ArangoDB / PostgreSQL (Apache AGE): Multi-model options if you want to reuse existing relational/document infra, though traversal syntax can be more complex.
Architectural Recommendation

Use Neo4j Enterprise / AuraDB for production multi-user developer tools or server-based AI agents. For standalone developer CLI agents or local desktop tools, start with KùzuDB to run graph queries entirely in-memory with zero Docker/database service setup.

3 Ingestion Pipeline Architecture

Building a Code & Document Graph requires a multi-stage parser and indexer pipeline that converts raw files into an enriched property graph.

Pipeline Steps

  1. AST Parsing with Tree-Sitter: Parse source files (Python, TypeScript, Go, Java) into universal AST trees. Extract class definitions, function signatures, parameters, docstrings, and imports.
  2. Symbol Table & Cross-File Linker: Resolve static method calls and class instantiations across file boundaries to form the directed call graph.
  3. Endpoint & Route Mapper: Identify framework decorators (e.g., `@app.get("/users")`, `@PostMapping("/orders")`, Express router definitions) and connect HTTP routes to handler methods.
  4. Docstring & Markdown Linking: Compute vector embeddings for docstrings, README sections, and API specs using OpenAI `text-embedding-3-small` or local BGE models. Create DOCUMENTS edges between docs and symbols.
  5. Graph Upsert: Write nodes and edges to Neo4j using batch Cypher queries for optimal ingestion speed.

4 Recommended Graph Schema for Code & Documentation

Below is the standard Node and Relationship schema designed for code intelligence and token optimization:

Node Types & Attributes

  • (:File {path, language, hash})
  • (:Class {name, filepath, docstring, signature})
  • (:Function {name, filepath, signature, docstring, start_line, end_line, body_summary})
  • (:Endpoint {http_method, path, framework})
  • (:Document {title, content_chunk, file_path, embedding})
  • (:Schema {name, fields})

Relationship Edges

  • (:File)-[:CONTAINS]->(:Class|Function)
  • (:Class)-[:HAS_METHOD]->(:Function)
  • (:Function)-[:CALLS]->(:Function)
  • (:Endpoint)-[:ROUTES_TO]->(:Function)
  • (:Function)-[:USES_SCHEMA]->(:Schema)
  • (:Document)-[:DOCUMENTS]->(:Function|Endpoint|Class)
  • (:Function)-[:OVERRIDES]->(:Function)

Sample Cypher Ingestion Script

// 1. Create Constraints and Vector Index
CREATE CONSTRAINT IF NOT EXISTS FOR (f:Function) REQUIRE f.id IS UNIQUE;
CREATE CONSTRAINT IF NOT EXISTS FOR (e:Endpoint) REQUIRE e.id IS UNIQUE;

CREATE VECTOR INDEX doc_embeddings IF NOT EXISTS
FOR (d:Document) ON (d.embedding)
OPTIONS {indexConfig: {`vector.dimensions`: 1536, `vector.similarity_function`: 'cosine'}};

// 2. Ingest Endpoint and link to Handler Function
MERGE (e:Endpoint {id: "POST /api/v1/orders"})
ON CREATE SET e.path = "/api/v1/orders", e.method = "POST";

MERGE (f:Function {id: "src/controllers/order.py::create_order_handler"})
ON CREATE SET f.name = "create_order_handler", 
              f.signature = "def create_order_handler(req: OrderRequest) -> OrderResponse",
              f.file_path = "src/controllers/order.py";

MERGE (e)-[:ROUTES_TO]->(f);

// 3. Link Function to Service Call
MERGE (s:Function {id: "src/services/order_service.py::process_payment"})
ON CREATE SET s.name = "process_payment",
              s.signature = "def process_payment(order_id: str, amount: float) -> bool";

MERGE (f)-[:CALLS]->(s);

5 Multi-Hop Graph Traversal Strategy for Context Retrieval

When an agent receives a prompt, it follows a 3-step hybrid retrieval pattern to construct a minimal sub-graph:

3-Step Hybrid Retrieval Workflow
  1. Entry Point Identification (Vector / Exact Match): Match user query against endpoint paths (exact match) or document/function embeddings (vector search) to locate 1–3 target seed nodes.
  2. Bounded Sub-Graph Expansion (1–3 Hops): Traverse outwards from seed nodes via CALLS, ROUTES_TO, and USES_SCHEMA edges up to depth N (typically 2 to 3 hops).
  3. Signature Context Formatting: Extract only node names, docstrings, type signatures, and relationship paths—leaving out implementation bodies unless specifically requested.

Cypher Retrieval Query Example

// Match Endpoint Node and fetch 2-hop execution context
MATCH (e:Endpoint {path: "/api/v1/orders", method: "POST"})-[:ROUTES_TO]->(handler:Function)
OPTIONAL MATCH path = (handler)-[:CALLS*1..2]->(downstream:Function)
OPTIONAL MATCH (handler)-[:USES_SCHEMA]->(schema:Schema)
RETURN 
    e.method + " " + e.path AS endpoint,
    handler.signature AS handler_sig,
    handler.docstring AS handler_docs,
    [nodes(path) | n.signature] AS call_chain,
    schema.fields AS request_schema;

Resulting Token Output to LLM Context Window (~600 tokens):

  - def create_order_handler(...) -> def process_payment(order_id: str, amount: float) -> bool

6 Incremental Codebase Updates (Git Integration)

Re-building the entire graph on every commit is slow and wasteful for large codebases. Graph RAG pipelines maintain graph consistency incrementally using Git commit hooks or CI/CD triggers.

Git Incremental Sync Strategy

  1. Identify Changed Files: Run git diff --name-only HEAD~1 HEAD to isolate modified, added, or deleted files.
  2. Delete Stale Sub-graphs: Remove existing AST nodes and outbound edges associated with modified file paths in Neo4j.
  3. Re-parse & Re-link: Execute Tree-Sitter parsing only on changed files and re-establish CALLS and ROUTES_TO edges to existing unchanged nodes.

Cypher Incremental Cleanup Example

// Clean up nodes for modified file
WITH "src/controllers/order.py" AS modifiedFile
MATCH (f:File {path: modifiedFile})-[:CONTAINS]->(symbol)
DETACH DELETE symbol;

MATCH (f:File {path: modifiedFile})
DETACH DELETE f;

8.1 AST Generation for Java Code in Python

Two main open-source Python solutions enable parsing Java source code into structured Abstract Syntax Trees:

  • tree-sitter with tree-sitter-java: High-performance, C-compiled parser with native Python bindings. Generates full CSTs/ASTs across all modern Java versions (Java 8 through Java 21+ features like Records, Sealed Classes, and Pattern Matching). Highly resilient to syntax errors.
  • javalang: A pure-Python parser for Java 8+. Provides a Pythonic class-based AST structure where nodes are instances of Python classes (`ClassDeclaration`, `MethodDeclaration`, `Annotation`, `MethodInvocation`).
  • LlamaIndex (CodeHierarchyNodeParser): Leverages Tree-sitter internally to chunk source code along AST structural boundaries (classes, methods) while retaining hierarchical parent-child relationships.

import javalang

java_code = """
package com.example.service;

import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    /**
     * Process incoming customer order.
     */
    @PostMapping("/create")
    public OrderResponse createOrder(@RequestBody OrderRequest request) {
        return orderService.processPayment(request);
    }
}
"""

tree = javalang.parse.parse(java_code)

for path, node in tree.filter(javalang.tree.MethodDeclaration):
    annotations = [ann.name for ann in node.annotations]
    params = [f"{p.type.name} {p.name}" for p in node.parameters]
    print(f"Method: {node.name}")
    print(f"  Return Type: {node.return_type.name if node.return_type else 'void'}")
    print(f"  Annotations: {annotations}")
    print(f"  Parameters: {params}")

8.2 Call Graph Construction for Java in Python

To generate a cross-file directed call graph ((:Function)-[:CALLS]->(:Function)) for Java:

  1. Symbol Table Generation: Scan all Java files in the workspace using Python to index class declarations (`package + className`), method signatures, and imported packages (`import com.example.service.OrderService;`).
  2. Invocation Traversal: Inspect `MethodInvocation` nodes within each method body. Match target method calls (e.g., `orderService.processPayment(...)`) against the symbol table by resolving field types (`orderService` -> `OrderService`) and method names (`processPayment`).
  3. Integration with Advanced Analyzers: For deep binary or bytecode-level analysis, developers can combine Python with Joern (a Code Property Graph platform) via its cpgql-python client to extract control-flow graphs (CFGs) and program dependence graphs (PDGs).

8.3 Endpoint Routing Extraction (Spring Boot & JAX-RS)

Modern Java applications expose REST APIs through framework annotations. Python AST parsers scan class and method annotations to build `(:Endpoint)` nodes and link them to handler methods via `(:Endpoint)-[:ROUTES_TO]->(:Function)`:

  • Spring Boot Annotations: `@RestController`, `@Controller`, `@RequestMapping`, `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`, `@PatchMapping`.
  • JAX-RS / Jakarta REST Annotations: `@Path`, `@GET`, `@POST`, `@PUT`, `@DELETE`, `@Consumes`, `@Produces`.

The Python extraction logic combines class-level base paths (e.g. `@RequestMapping("/api/v1/orders")`) with method-level sub-paths (e.g. `@PostMapping("/create")`) to form full URI routes (e.g. POST /api/v1/orders/create).

8.4 Javadoc & Technical Documentation Linking

Java documentation exists as Javadoc comments above classes/methods (`/** ... */`) or external Markdown/OpenAPI specification files.

  • Javadoc Extraction: `javalang` or `tree-sitter` extracts docstrings attached to class and method AST nodes.
  • Embedding & Linking: Use open-source Python embedding libraries such as sentence-transformers (e.g. `all-MiniLM-L6-v2` or `bge-small-en-v1.5`) or langchain-embeddings to generate vector representations for docstrings and Markdown chunks.
  • Neo4j Integration: Store vector embeddings directly on `(:Document)` and `(:Function)` nodes in Neo4j, enabling both keyword/graph traversal and semantic vector search.

8.5 Complete Python Implementation: Parsing Java Code & Ingesting into Neo4j

The following standalone Python script parses Java source files, extracts AST symbols, call paths, Spring Boot endpoint annotations, and Javadocs, and batch-ingests the resulting graph directly into Neo4j using the official neo4j Python driver: 

import os
import javalang
from neo4j import GraphDatabase
from sentence_transformers import SentenceTransformer

class JavaGraphIngestor:
    def __init__(self, uri, auth):
        self.driver = GraphDatabase.driver(uri, auth=auth)
        self.embedder = SentenceTransformer('all-MiniLM-L6-v2')

    def close(self):
        self.driver.close()

    def setup_schema(self):
        with self.driver.session() as session:
            # Constraints
            session.run("CREATE CONSTRAINT IF NOT EXISTS FOR (c:Class) REQUIRE c.id IS UNIQUE;")
            session.run("CREATE CONSTRAINT IF NOT EXISTS FOR (f:Function) REQUIRE f.id IS UNIQUE;")
            session.run("CREATE CONSTRAINT IF NOT EXISTS FOR (e:Endpoint) REQUIRE e.id IS UNIQUE;")
            # Vector Index for Javadoc / Code Search
            session.run("""
            CREATE VECTOR INDEX java_doc_embeddings IF NOT EXISTS
            FOR (d:Document) ON (d.embedding)
            OPTIONS {indexConfig: {`vector.dimensions`: 384, `vector.similarity_function`: 'cosine'}};
            """)

    def parse_and_ingest_java(self, file_path, java_code):
        tree = javalang.parse.parse(java_code)
        package = tree.package.name if tree.package else "default"
        
        classes = []
        methods = []
        endpoints = []
        calls = []
        docs = []

        for _, class_node in tree.filter(javalang.tree.ClassDeclaration):
            class_id = f"{package}.{class_node.name}"
            classes.append({
                "id": class_id,
                "name": class_node.name,
                "package": package,
                "file_path": file_path
            })

            # Extract Class-Level Base Route (Spring Boot)
            base_route = ""
            for ann in class_node.annotations:
                if ann.name in ["RequestMapping", "Path"]:
                    if ann.element:
                        base_route = str(ann.element).strip('"')

            for method_node in class_node.methods:
                method_id = f"{class_id}::{method_node.name}"
                sig = f"{method_node.return_type.name if method_node.return_type else 'void'} {method_node.name}()"
                doc = method_node.documentation or ""

                methods.append({
                    "id": method_id,
                    "name": method_node.name,
                    "signature": sig,
                    "docstring": doc,
                    "class_id": class_id
                })

                if doc:
                    emb = self.embedder.encode(doc).tolist()
                    docs.append({
                        "id": f"doc::{method_id}",
                        "text": doc,
                        "symbol_id": method_id,
                        "embedding": emb
                    })

                # Extract Spring Boot / JAX-RS Endpoint Routing
                for ann in method_node.annotations:
                    http_method = None
                    sub_path = ""
                    if ann.name in ["GetMapping", "PostMapping", "PutMapping", "DeleteMapping"]:
                        http_method = ann.name.replace("Mapping", "").upper()
                        if ann.element:
                            sub_path = str(ann.element).strip('"')
                    elif ann.name in ["GET", "POST", "PUT", "DELETE"]:
                        http_method = ann.name

                    if http_method:
                        full_path = f"{base_route}{sub_path}"
                        endpoints.append({
                            "id": f"{http_method} {full_path}",
                            "method": http_method,
                            "path": full_path,
                            "handler_id": method_id
                        })

                # Extract Internal Method Invocations (Call Graph)
                for _, inv_node in method_node.filter(javalang.tree.MethodInvocation):
                    calls.append({
                        "caller_id": method_id,
                        "callee_name": inv_node.member
                    })

        self._batch_upsert(classes, methods, endpoints, calls, docs)

    def _batch_upsert(self, classes, methods, endpoints, calls, docs):
        query = """
        UNWIND $classes AS c
        MERGE (cls:Class {id: c.id})
        ON CREATE SET cls.name = c.name, cls.package = c.package, cls.file_path = c.file_path;

        UNWIND $methods AS m
        MERGE (f:Function {id: m.id})
        ON CREATE SET f.name = m.name, f.signature = m.signature, f.docstring = m.docstring
        WITH m, f
        MATCH (cls:Class {id: m.class_id})
        MERGE (cls)-[:HAS_METHOD]->(f);

        UNWIND $endpoints AS e
        MERGE (end:Endpoint {id: e.id})
        ON CREATE SET end.method = e.method, end.path = e.path
        WITH e, end
        MATCH (f:Function {id: e.handler_id})
        MERGE (end)-[:ROUTES_TO]->(f);

        UNWIND $docs AS d
        MERGE (doc:Document {id: d.id})
        ON CREATE SET doc.text = d.text, doc.embedding = d.embedding
        WITH d, doc
        MATCH (f:Function {id: d.symbol_id})
        MERGE (doc)-[:DOCUMENTS]->(f);
        """
        with self.driver.session() as session:
            session.run(query, classes=classes, methods=methods, endpoints=endpoints, docs=docs)

if __name__ == "__main__":
    ingestor = JavaGraphIngestor("bolt://localhost:7687", ("neo4j", "password"))

8.6 Complete Python Implementation: Retrieving Java Sub-Graph Context from Neo4j based on Prompt

When a user asks a question (e.g., "Explain how order creation and payment processing work for POST /api/v1/orders/create"), the following Python script uses vector similarity and multi-hop Cypher queries to extract a minimal, token-optimized context sub-graph: 

from neo4j import GraphDatabase
from sentence_transformers import SentenceTransformer

class JavaGraphRetriever:
    def __init__(self, uri, auth):
        self.driver = GraphDatabase.driver(uri, auth=auth)
        self.embedder = SentenceTransformer('all-MiniLM-L6-v2')

    def close(self):
        self.driver.close()

    def retrieve_context_for_prompt(self, user_prompt: str, endpoint_path: str = None) -> str:
        """
        Retrieves a token-optimized sub-graph for an LLM prompt.
        """
        context_lines = []

        with self.driver.session() as session:
            # 1. Direct Route Matching (if prompt mentions an endpoint)
            if endpoint_path:
                route_query = """
                MATCH (e:Endpoint) WHERE e.id CONTAINS $endpoint
                MATCH (e)-[:ROUTES_TO]->(handler:Function)
                OPTIONAL MATCH path = (handler)-[:CALLS*1..3]->(downstream:Function)
                OPTIONAL MATCH (handler)<-[:HAS_METHOD]-(cls:Class)
                RETURN e.id AS endpoint, 
                       cls.id AS controller_class,
                       handler.signature AS handler_sig,
                       handler.docstring AS handler_doc,
                       [n IN nodes(path) | n.signature] AS call_chain
                """
                results = session.run(route_query, endpoint=endpoint_path).data()
                
                for row in results:
                    context_lines.append(f"=== ENDPOINT CONTEXT ===")
                    context_lines.append(f"Endpoint: {row['endpoint']}")
                    context_lines.append(f"Controller Class: {row['controller_class']}")
                    context_lines.append(f"Handler Signature: {row['handler_sig']}")
                    if row['handler_doc']:
                        context_lines.append(f"Handler Documentation: {row['handler_doc']}")
                    if row['call_chain']:
                        context_lines.append(f"Execution Call Chain: {' -> '.join(row['call_chain'])}")

            # 2. Vector Search over Javadoc / Documentation
            prompt_embedding = self.embedder.encode(user_prompt).tolist()
            vector_query = """
            CALL db.index.vector.queryNodes('java_doc_embeddings', 3, $embedding)
            YIELD node AS doc, score
            MATCH (doc)-[:DOCUMENTS]->(f:Function)<-[:HAS_METHOD]-(c:Class)
            RETURN c.name AS className, f.name AS methodName, f.signature AS signature, doc.text AS javadoc, score
            """
            doc_results = session.run(vector_query, embedding=prompt_embedding).data()

            if doc_results:
                context_lines.append("\n=== SEMANTIC MATCHED FUNCTIONS & JAVADOC ===")
                for r in doc_results:
                    context_lines.append(f"Class: {r['className']} | Method: {r['signature']} (Score: {r['score']:.2f})")
                    context_lines.append(f"Javadoc: {r['javadoc']}")

        return "\n".join(context_lines)

# Example Execution
if __name__ == "__main__":
    retriever = JavaGraphRetriever("bolt://localhost:7687", ("neo4j", "password"))
    
    prompt = "How does payment processing work during order creation?"
    context = retriever.retrieve_context_for_prompt(
        user_prompt=prompt, 
        endpoint_path="POST /api/v1/orders/create"
    )
    
    print("--- CONTEXT SENT TO LLM (Token Size: ~350 tokens) ---")
    print(context)
    retriever.close()
